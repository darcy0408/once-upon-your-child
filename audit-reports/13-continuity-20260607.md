# Continuity & Bus-Factor Audit — SPOF and Vendor Lock-In

Date: 2026-06-07
Scope: People, knowledge, infrastructure, vendors, data, code, and identity for
Once Upon YOUR Child / Story Weaver — a Flutter + Flask therapeutic AI
storytelling app built and operated by a single developer (Darcy). The objective
is reducing project mortality risk: ensuring a competent successor, or a
recovered Darcy after a long absence, can resume operating the product within
days.
Method: Static audit from the repository only (`C:\dev\sw-audits`, clean
origin/main checkout). Read-only — no account configs or code were modified.
Where a fact is knowable only from a vendor dashboard not visible here, it is
marked "Unverified — verify" and scored on the worst plausible case. Secrets
were never logged or echoed.

## Executive Summary

The largest risk to this product is not technical — it is the concentration of
every account, secret, deploy capability, and operational memory in one person,
with no authorized second party and almost no off-machine externalization. If
Darcy were unreachable tomorrow, the app keeps *running* (Railway self-heals,
provider fallbacks cover blips, backups run on a cron), but it cannot be
*recovered, changed, or transferred* by anyone else, and two losses would be
permanent.

The two unrecoverable single points of failure:

1. The Android release keystore (CONT-01). MT-144 is still OPEN — the keystore
   has not even been created yet. Once it is, the runbook (STORE-10) puts it only
   on Darcy's machine with no mandated off-machine backup. A lost keystore means
   no future Play Store update is ever possible. This is Critical regardless of
   RTO.
2. `ENCRYPTION_KEY` (CONT-02), the AES-256-GCM key that encrypts every stored
   BYOK API key (`backend/encryption_utils.py`). It lives only in Railway env,
   is in no documented vault, and if lost permanently bricks all stored encrypted
   keys — a secret recoverable only from one place, touching user data.

The scariest *transient* gaps if Darcy vanished:

- No authorized second party exists for any account (GitHub, Railway,
  Cloudflare, Stripe, the domain). Nobody else can log in, deploy, restore, or
  transfer ownership (CONT-03, CONT-04).
- The dev machine is a Critical SPOF: it holds local `.env` secrets, the future
  keystore, and — crucially — the operational knowledge. There is no `CLAUDE.md`
  or `AGENTS.md` in the repo; the hard-won landmines (parallel git-index race,
  gstatic dual-CSP rule, Stripe v15 breaking changes, Railway deploy-log gotcha)
  live in machine-local `~/.claude/memory` and across 198 session logs, not in a
  single discoverable in-repo runbook (CONT-05, CONT-06).
- The Postgres backup runs daily to R2, but the RESTORE is undocumented and
  untested, and the backup failure path is silent (it already ran silent for five
  days, MT-220). There is no DR or "prod down, founder unreachable" runbook
  (CONT-07, CONT-08).

The good news that lowers the floor: data export and deletion are self-service
and audit-logged (`/api/user/<id>/export`, `/api/user/<id>/data`); prompt
templates are versioned in code; deploy topology is captured in `railway.toml`;
and the off-Railway R2 backup defeats Railway account loss for the data itself.

The single highest-impact, smallest-effort fix is to stand up an emergency
credential vault and name one authorized second party (CONT-03). It is a few
hours of work and it converts most "weeks / unrecoverable" rows in the SPOF map
into "days."

## SPOF Inventory

Full machine-readable inventory: `audit-reports/spof-map.csv` (23 items). The
concentration pattern: Owner = Darcy and Authorized Second Party = None on every
row. Grouped by domain:

### Identity & accounts (all owner = Darcy, all 2nd-party = none)

GitHub, Railway, Cloudflare, Stripe, Google AI/Gemini, OpenRouter, ElevenLabs,
Replicate, Resend, Firebase, Sentry, domain registrar, Apple Developer, Google

Unverified for every account; the worst plausible case (no recovery path, no
second party) is assumed for scoring. The domain registrar identity is not even
discoverable from the repo (CONT-09).

### Secrets

- Critical, unrecoverable: `ENCRYPTION_KEY` (BYOK key encryption), Android
  keystore. Both single-copy, both touch the no-second-copy boundary.
- Recoverable by regeneration with user impact: `JWT_SECRET_KEY`, `SECRET_KEY`
  (sessions invalidated), all per-vendor API keys (re-issue).
- GitHub Actions repo secrets (~10: RAILWAY_TOKEN, CLOUDFLARE_*, R2_*,
  DATABASE_PUBLIC_URL, NETLIFY_*) — names documented in `postgres-backup.yml` and
  `DEPLOYMENT_SECRETS_GUIDE.md`; values are not, and re-issuing all of them is a
  multi-vendor scramble (CONT-10).

### Infrastructure

Railway project `radiant-tranquility` (`36b27716-...`) runs backend, worker
(`lovely-perfection`), `celery-beat`, Redis, and Postgres (`cfbe4566-...`).
Topology is well captured in `railway.toml`, including the load-bearing detail
that beat must be its own service (`-B` is incompatible with `--pool=solo`) or
the COPPA retention purge never fires. Frontend is Cloudflare Pages.

### Knowledge

Prompt templates + age constraints are externalized in code and versioned
(low risk). Everything operational is not: no `CLAUDE.md`/`AGENTS.md`, no
`docs/env_vars_reference.md` (referenced by `.env.example` but ABSENT —
CONT-11), no DR/restore/succession runbook. The operating memory is in
machine-local files and 198 dated session logs.

### The dev machine

The convergence point: local `.env`, the future keystore + `key.properties`
passwords, BYOK test keys, and the knowledge store. Loss without external backup
is the worst recovery scenario in the inventory.

prohibition on child-directed apps is a forcing function to migrate regardless.

## Succession Plan Template

Full, fill-in-the-blanks template: `audit-reports/succession-plan-template.md`.
It is usable as-is and covers all four absence scenarios:

- 1 day: nothing breaks; second party only acknowledges P1 alerts.
- 1 week: automated work continues; a human must watch the silent backup and
  Stripe-webhook failure paths.
- 1 month: add domain renewal, key rotation, deadline-driven backlog triage.
- Indefinite: parallel ownership transfer of GitHub/Railway/Cloudflare/Stripe/
  domain, vault handover, keystore handover, and a proven restore drill.

It also contains the credential inventory grid, the deploy-from-scratch runbook
(with the undocumented manual steps called out), the DR/restore drill, and a
quarterly resilience checklist.

### Test scenario — "Darcy unavailable 2 weeks"

What does NOT break: story generation, payments, illustration, backups, and the
daily retention purge all run unattended; Railway restarts failed services; the
TTS and image fallback chains absorb single-provider outages.

What breaks or rots silently: a failed nightly backup raises no alert (manual
Actions check only); Stripe webhook failures are log-only; a full
all-providers-down event surfaces only in Sentry at `warning`. None of these has
a second human watching.

What a second party would need to hold steady state: read access to Sentry,
Railway, Stripe, and GitHub Actions, plus this document. To *fix* anything they
additionally need the vault (Section 1) — which today does not exist. That is the
gap this audit's top recommendation closes.
