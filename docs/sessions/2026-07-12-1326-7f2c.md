The initial B commit stored `latestOrderId` as `store_transaction_id`, but that value increments on every renewal — so a Real-Time Developer Notification (which carries the purchase token) could never link back to the purchase row, violating the `IapPurchase.store_transaction_id` contract (`backend/models/iap_event.py` documents Google's key as the purchase token). `_verify_with_google` now sets `store_transaction_id = purchase_token`; a test asserts the persisted row is keyed by the token. Pure mapping (`_map_apple_receipt`) split out; fails closed: missing secret / 21004 → 503, bad receipt → 400, Apple outage (21005) → 502. The verify call now threads `product_id` through. **Design choice: Option 2 (`verifyReceipt` + shared secret)** — chosen over the App Store Server API because it directly consumes the receipt the client already sends and needs only one owner credential; it is Apple's legacy-but-functional endpoint, and migrating to the Server API (StoreKit2 signed transactions) is a post-launch hardening step.
