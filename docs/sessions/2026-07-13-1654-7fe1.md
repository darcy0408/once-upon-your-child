**1. PR #432 — MT-350 chunk D: Apple + Google server-to-server notification handlers — MERGED to `main` (`0166f82c`).**
The last IAP code chunk. The Phase-1 ACK-only stub (`_handle_notification_stub`) in `backend/routes/iap_routes.py` is gone; store-side **renewals, cancellations and refunds now update entitlement**. Before this, a subscription verified once via `/api/iap/*/verify` would never auto-downgrade on a store-side cancel or refund.

- **Apple** (`POST /api/iap/apple/notifications`, App Store Server Notifications V2): the already-verified outer `signedPayload` JWS is decoded, then the inner `data.signedTransactionInfo` JWS is verified with the same Apple-root-CA chain (`verify_apple_jws`) before any field of it is trusted. Dedup on `notificationUUID` (unique insert into `IapNotificationEvent`, committed atomically with the entitlement write). State mapping: REFUND/REVOKE/`revocationDate` → `refunded`; DID_FAIL_TO_RENEW → `grace_period` (GRACE_PERIOD subtype) or `on_hold`; EXPIRED/GRACE_PERIOD_EXPIRED → `expired`; otherwise the transaction's own expiry window, with a **missing expiry failing closed** to inactive. DID_CHANGE_RENEWAL_STATUS also sets `cancel_at_period_end`. Ordering guard: a payload whose `signedDate` predates the row's `last_event_time` is dropped as stale (an out-of-order old EXPIRED cannot regress a newer DID_RENEW). **Credential-free — fully testable today.**
- **Google** (`POST /api/iap/google/notifications`, Real-Time Developer Notifications via Pub/Sub push): `message.data` base64-decoded; dedup on the Pub/Sub `messageId`. The RTDN body is only used to *locate* the subscription — the authoritative state is **re-queried** from the Play Developer API via the same `_verify_with_google` path the verify endpoint uses (missing creds → 503 *before* the dedup row is written, so redelivery converges after config; Play API down → 502). `voidedPurchaseNotification` (refund) is applied directly as `refunded`. A failed re-query **never revokes** (log + ACK).
- **Both stores:** an unknown transaction/purchase-token returns **404 with nothing committed**, so the store's retry converges once the client `/verify` call creates the `IapPurchase` row (the purchase notification often races the verify by seconds). All writes flow through the shared `_upsert_iap_purchase` (ordering + ownership guards) and `apply_entitlement()`.

## Decisions
- **Unknown purchase → 404 (retry), not a blind ACK:** the purchase notification can beat the client's `/verify` call by seconds; a non-2xx makes Apple retry (1h/12h/24h/48h/72h) and Pub/Sub redeliver with backoff, converging once the row exists. Trade-off: notifications for purchases that never verify (e.g. deleted accounts, whose `IapPurchase` rows are erased) will retry until the store gives up — accepted as observable noise.
- **Google state is re-queried, never taken from the notification body**; consequently Google needs no payload-level staleness guard (`event_time` = query time, matching the verify endpoint). Apple state IS payload-derived, hence its explicit `signedDate` stale-drop.
- **Google re-query failure never revokes** — revoking off a failed lookup would let an outage downgrade paying users.
- **`IOS_BUNDLE_ID` is optional** (skip check when unset) so notifications stay credential-free-testable; the unknown-txn 404 is the real gate.
- **Ran the session on Fable** (owner choice): safety-critical payment code + the Fable weekly bucket resets 2026-07-14 and was otherwise unused, while Opus draws from the constrained all-model bucket.
